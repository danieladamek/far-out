## 1. Hard rules

- **Never invent content.** Definitions, summaries, explanations, figures, thresholds, dates, dollar amounts — all come from `content-pack/`. If something is missing, render an amber `TODO(author)` marker (`.bx-todo`) and list it on `/methods`. Do not fill gaps from your own knowledge. Federal contracting rules change often and you do not know the current ones.
- **Body text is rendered as written.** Structure it, link it — never rewrite or paraphrase `review.md`, a record's `what`, or any other pack prose.
- **Uncited prose fails the build.** Any block of ≥ 25 words in `review.md` or in a concept body with no `[n]` and no `<!-- framing -->` marker (immediately before it, or inside the block) is a content-build error (APP-SPEC §6.1). List it in `BUILD-ERRORS.md` and surface it on `/methods`. **Do not fix it by adding a citation.** Record prose in the extension files is cited the same way and counts as citing text for the "reference never cited" check: a reference cited only from a record is cited.
- **`<!-- synthesis -->` blocks stay visible.** Render them with a quiet left rule and a "synthesis" label, give each an id, and link every one from `/methods`. Never strip the marker.
- **Nothing implies peer review, official status, or advice.** `manifest.venue` and `manifest.disclaimer` say what this is; render the disclaimer in the footer of every page and in full on `/about`. `as_of` appears on `/`, `/read` and `/about`, and every record page shows its own `as_of`. No page uses the second person imperative to tell a reader what to do about their own business ("the rule requires…" is fine; "you should…" is not); if pack text does, it is a pack error — record it, do not render it changed.
- **No firm is tailored for.** There is no account, no server-side state, no analytics beacon. Personalisation (NAICS codes, certifications held, keywords, the notepad, saved filters) lives in `localStorage` only, with a visible "stays in this browser" note. The two things that do leave the browser are stated plainly where they happen: `/partners` queries the USAspending API live, and `/find` loads this site's own harvested data files.
- **Where sources disagree, show both.** A record's `conflicts` list and any `key_facts` line beginning `[CONTRADICTED …]` or `[unconfirmed …]` render visibly as such (see §4b); never pick one figure silently. The reference's `recheck`, `rechecked`, `dropped_quotes` and `recheck_note` fields render on its card.
- **Pending is pending.** `pending_changes[]` renders as a labelled block on each record with its status word and date; a `class-deviation` entry is where the FAR-overhaul numbering lives. The codified FAR number is the primary citation everywhere.
- **No runtime fetches of pack content.** Everything in `content-pack/` ships in `dist/`. The only runtime network calls are the two named above.
- **Fail loudly in the content build.** Schema violation, unresolved `[n]`, unknown term/concept/route/gate/program id, missing data file, ambiguous term variant → non-zero exit with a clear list. Do not "fix" the pack silently; write `content-pack/BUILD-ERRORS.md` and continue building the app with whatever validated (the errors also surface on `/methods`).
- **Delivery mode is `pages`** and it is not yours to change. The app ends up public — see §6b.
- **GitHub identity:** `danieladamek`. Verify with `gh auth status` before any push. **The repo already exists** at `github.com/danieladamek/far-out` with the content pack and a probe workflow; do not `gh repo create`. Pull first.

## 4b. The FAR Out surfaces — normative spec for this build

The guide is organised situation-first: a pathfinder leads into a catalogue of routes in four families; every route carries its gates, its programs, a saved search into `/find`, and its sources. These are what Daniel asked for by name.

### Pack extensions (validate these; fail loudly on a violation)

- `routes.yaml` — 50 records: `id`, `name`, `family` (sbir-sttr | setaside-vehicle | partnering | ot-cso), `governing_text`, `what`, `who_for`, `how_it_works[]` (or `benefits[]`/`requirements[]`), `steps[]`, `gates[]` (gate ids), `programs[]` (program ids, optional), `situations[]` (pathfinder tags), `modifiers{}`, `find_filter{}` (optional), `official_url`, `pending_changes[]`, `as_of`, `sources[]`, `conflicts[]`.
- `programs.yaml` — 134 records: programs, vehicles, front doors, transition programs, consortia and consortium managers; `family`, `kind`, `status` (live | unconfirmed | empty), `cycle{}`, `awards[]`, `membership{}` for consortia, and the common fields.
- `certifications.yaml` (8), `gates.yaml` (60), `buyers.yaml` (40: eight `kind: buyer-pathway` records and 32 agency small-business offices with `forecast_url`), `help.yaml` (47), `primes.yaml` (24), `mechanics.yaml` (6), `changes.yaml` (55: `id`, `date`, `status`, `what`, `affects[]`, `sources[]`, `basis`), `queries.yaml` (674), `pathfinder.yaml` (questions, per-route tags, the ranking rule).
- Every `[n]` in any field resolves; every id in `gates[]`, `programs[]`, `affects[]` resolves to a record; `situations[]` values are from the five pathfinder tags; a `find_filter.feed` is one of `sam | grants | both | none`.

### Routes and behaviour

- **`/` — the pathfinder.** The front door. Render `pathfinder.questions` as a short form (one screen; answers persist in `localStorage`; a "clear my answers" control). Rank routes by `pathfinder.rule` exactly as written (situation tag match 2 points, modifier match 1 point; `certs` matched against the firm's answered certifications; score 0 hidden; `always_show` always shown). Show the ranked routes grouped by family with **why each matched** (the matched tags, in words from the question labels). Do not compute or show any other score, and never label a route "best" or "recommended"; the page says in the pack's words that the ranking is a count of matches, not advice. Below the results: the four family cards linking to `/routes?family=…`, the "what changed" strip (latest five `changes` entries), and the `as_of` date. `fig6` (`route-decision`) is the same logic as a picture; link it.
- **`/routes`, `/routes/:id`.** The catalogue, filterable by family, situation tag, modifier, gate and whether a `find_filter` exists. A route page renders every field in a fixed order: `what` (with term links and citation fold-outs) → `who_for` → `how_it_works` / `benefits` / `requirements` / `steps` → **gates required** (chips linking to `/gates#id`, each with its one-line `what`) → **programs under this route** (cards from `programs.yaml`) → **find opportunities** (a button that opens `/find` with the route's `find_filter` applied, or "no public feed carries this route; here is the official page" when `feed: none`) → `pending_changes` (labelled block, status word + date) → `conflicts` (labelled "Where official sources differ") → `official_url` → sources (reference cards) → `as_of`. A notepad anchor per route.
- **`/programs/:id`.** Same pattern; for `kind: consortium` render `membership` (eligibility, fees by tier exactly as posted, how to join, what it gives), `fees_on_awards`, `non_member_visibility`, `opportunity_process`, manager and sponsors; for vehicles render `status`, `ordering`, `obligations`. A program whose `status` is `unconfirmed` or empty shows a visible "not confirmed as live on {as_of}" banner with the `conflicts`/`status_note` text.
- **`/status`.** The certifications and size records: each with eligibility, benefits (sole-source and set-aside thresholds, price preference), **the FAR-vs-13 CFR figures side by side where they differ**, steps, cost and time, recertification, pending changes, sources. `fig5` (`goals-vs-results`) sits on this page.
- **`/gates`, `/gates#id`.** Checklists: group by the gate's `applies_when` (nearly every route · above a threshold · by what the work touches · by contract type · getting paid · OT-specific — derive from the gate fields, do not hard-code), each gate as a disclosure with `what`, `applies_when`, `steps`, `cost_time`, `official_url`, pending changes, sources. The CMMC gate renders `rule` and `suspension` as two separate labelled blocks and marks `secondary_only` items as "reported by secondary sources only". `fig1` (`thresholds-2025`) sits here. A gate page shows which routes require it.
- **`/buyers`.** Two parts. The buyer's map: the eight `kind: buyer-pathway` records (six AAF pathways, the civilian model, the grants model) each with governing text and date, timelines, decision authority, `industry_entry` exactly as the text states it, pending changes (secondary-only items marked). Then the agency directory: 32 small-business offices with `forecast_url` (verified ones first; unverified marked), `what_else`, sources.
- **`/help`.** Help-organisation types, outreach and matchmaking programs (with cadence and how to register), and the directories of primes; filterable by kind; secondary-only records marked.
- **`/primes`.** One card per prime, rendering **only what the company's own page says** (`registration_asks`, `liaison_named`, `programs`, `selection_statement`, `forecast_statement`, `unreadable`), with the supplier portal link, the `as_of`, and the note that the card records the company's page as read on that date. No ranking, no commentary.
- **`/how`.** The `mechanics.yaml` records as short pages: reading a SAM.gov notice (notice-type and set-aside codes as tables), market research from the firm's side, responding (sources sought, capability statement), payment, OTs in public data.
- **`/changes`.** The dated ledger from `changes.yaml`, newest first, filterable by status and theme, each entry linking to the records it `affects` and to its sources; `basis` shown where present ("secondary-only", "unread", "unconfirmed"). `fig7` (`changes-timeline`) sits here. The strip on `/` reads from the same data.
- **`/find` — the opportunity search.** Client-side search over the harvested data in `public/data/opportunities/` (§4c). Filters: keyword (title + agency + the stored description excerpt), feed (SAM / Grants), notice type, set-aside code, NAICS prefix, agency, response-deadline window, posted window, and an "SBIR/STTR" toggle (records whose title matches `/\bS[BT]IR\b|\bSTTR\b/i`, tagged at harvest). Saved filters: every route's `find_filter`, plus the firm's own NAICS codes and keywords from `localStorage`. Each result links to its SAM.gov or Grants.gov page; nothing is proxied. The page states the harvest date (from the data's manifest), that notices are up to a day old, that the SAM data is the public daily extract and the Grants.gov data the public search API, and that SBIR.gov and the DoD SBIR/STTR portal are linked but not harvested. If the data files are missing (a local build without a harvest), the page says so and shows the deep links instead; it never errors.
- **`/partners` — who wins and who subcontracts.** Live queries to `api.usaspending.gov` (no key; CORS open as of the probe): inputs NAICS code (required), optional state and set-aside type, a date window defaulting to the last 12 months. Show top recipients by obligation (`/api/v2/search/spending_by_category/recipient/`), the matching award count, and a subaward view (`spending_by_award` with `subawards: true`) listing prime recipient → subawardee pairs. Each recipient links to its USAspending profile. State on the page that these queries leave the browser and go to USAspending, that nothing else is sent, and the API's own "data may be incomplete" caveat for subawards. Cache responses in `sessionStorage` for the session; handle a failed request with a plain message and the manual link.
- **Record pages everywhere** render `key_facts` lines beginning `[CONTRADICTED on recheck …]` or `[unconfirmed on recheck …]` only inside the reference card, styled as such; they never appear as plain facts in a record body.

## 4c. The harvest and the workflows

- **`scripts/harvest/sam.mjs`:** stream the public SAM.gov daily extract (`https://s3.amazonaws.com/falextracts/Contract%20Opportunities/datagov/ContractOpportunitiesFullCSV.csv`, ~216 MB; parse it streaming, never load it whole), keep rows where `Active == Yes` and (`ResponseDeadLine` is empty or ≥ today − 1 day, or `Type` ∈ {Sources Sought, Presolicitation, Special Notice} posted within 120 days), and write slim records: `id, title, sol, agency, subtier, office, posted, type, setAsideCode, setAside, deadline, naics, psc, popState, link, descExcerpt (first 400 chars), sbir (bool)`. Shard by NAICS two-digit sector into `public/data/opportunities/sam/<sector>.json` plus `index.json` (counts, harvest time, columns). Target ≤ 1.5 MB per shard before compression.
- **`scripts/harvest/grants.mjs`:** `POST https://api.grants.gov/v1/api/search2` with `oppStatuses: "posted|forecasted"`, paging by `rows`/`startRecordNum` until `hitCount` is covered; keep `id, number, title, agency, agencyCode, openDate, closeDate, oppStatus, docType, cfdaList, eligibilities (23 = small business flag), sbir (bool)`; write `public/data/opportunities/grants/all.json` and fold counts into `index.json`.
- **Both** write `public/data/opportunities/manifest.json` (`harvestedAt`, counts, source URLs, failures) and exit non-zero on a failed source **but** leave the other source's output in place; the app reads `failures` and says which feed is stale.
- **`.github/workflows/deploy.yml`:** `npm ci → npm test → npm run build:content → npm run harvest → npm run build` (with `BASE_PATH=/far-out/`) → copy `dist/index.html` → `dist/404.html` → `actions/upload-pages-artifact` → `actions/deploy-pages`. Triggers: push to `main`, `workflow_dispatch`, and `schedule: cron "17 9 * * *"` (daily; the schedule run only re-harvests and redeploys). The harvest output is **never committed**; `public/data/opportunities/` is in `.gitignore`. Use the current major versions of `actions/checkout`, `actions/setup-node`, `actions/upload-artifact`, `actions/upload-pages-artifact`, `actions/configure-pages` and `actions/deploy-pages` that run on Node 24 (the v4 line was flagged as Node-20-deprecated on the probe run).
- **`.github/workflows/probe-sources.yml` and `scripts/probe-sources.mjs`:** keep, but make the script exit non-zero when any probe returns a non-2xx/206 status so a blocked feed shows red; bump the action versions as above; keep the Markdown summary.
- **Local builds** (`npm run build` on Daniel's machine) must not require the harvest: `npm run harvest` is a separate script, and `/find` degrades as described in §4b when the data folder is absent.
